How it works

A password is a calculation, not a record.

The same inputs always give the same password, so there's nothing to save, sync or steal. Change one input and you get a completely unrelated password.

Inputs (not secret)site, login, version
↓
Phone's secure chipHMAC-SHA256 with the 128-bit master, only after a fingerprint touch
↓ site key
In the app, then wipedsite key → byte stream → allowed characters, no bias, rules applied
// setup, once master = 16 random bytes // shown once as 12 words for your paper backup import master into the secure chip // non-exportable, fingerprint required for every use wipe the app's copy // every password message = "rekey-v1" + site + login + version // length-prefixed fields site key = HMAC-SHA256(master, message) // inside the chip stream = HMAC-SHA256(site key, 0, 1, 2 …) // normal software password = stream mapped onto the allowed characters with rejection sampling

The algorithm is frozen as rekey-v1 and pinned by 56 test vectors, so a password made today is the same password in ten years. A change would be a new version, never an edit.

What's different

Not a vault, and no password to remember.

There are two common ways to handle many passwords. Rekey takes a third.

In the app

Everything a password needs, nothing it doesn't.

⚡

It detects the site

Autofill reads the page's domain or the app asking, reduces it to the real registrable domain, and offers only the matching entry. You type nothing.

↻

Password change in one tap

A site forced a new password? Raise its version and you get an unrelated one. The previous version is still one touch away for the "old password" field.

⚙

Rules per site

20 characters with every class by default. A site that bans symbols or caps the length gets its own rules, saved with the entry.

⧉

Master generations

Worried your 12 words leaked? Make a new master and move sites over one at a time; each site remembers which generation it uses.

⇅

Export and restore

Export the site list as JSON. On a new phone, type the 12 words, import the list, and every password comes back exactly.

◐

Light, dark or system

Coloured letter avatars, version labels, recently used sites as tiles, and a strip that says whether autofill is on.

Security details

Built to fail closed.

  • No internet permission. The app can't send anything anywhere, and the manifest proves it.
  • The fingerprint is the lock, not the key. Phones never give apps the fingerprint itself. It only releases the chip's key, and enrolling a new finger destroys that key.
  • One chip operation per touch. A fingerprint-bound key allows one use per touch. That one use makes a 32-byte site key, and software stretches it to the password's length.
  • Screens are secure. Screenshots and the recent-apps preview are blocked; shown passwords are wiped from memory when you leave the screen.
  • Browsers must be trusted once. Any app can claim its fields belong to a website. Rekey only believes a browser you confirmed, and pins its signing certificate.
  • https only, one origin per fill. Plain http is refused, and a login inside an embedded frame can't receive the parent page's password.
  • Apps match by package. A native app is linked to a site once; nothing is guessed from its name.
  • The public suffix list is bundled. co.uk-style domains are handled correctly, and the list is never downloaded at runtime.

How it's built

Kotlin and Jetpack Compose, Android 9 and newer. The password maths lives in a pure-Kotlin module with no Android code, so it's tested on its own against frozen vectors and a reference implementation. Keys live in the Android Keystore (StrongBox when the phone has it), with an AES-wrapped fallback for phones that can't import an HMAC key. The 12 words follow the BIP39 word list.
